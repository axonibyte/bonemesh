# Known-defect registry

Every defect found by review or testing gets a row here, from discovery through
fix through gate verification. This registry serves double duty:

1. The fix list for hardening work.
2. The **validation-gate corpus** (testing-methodology): once the harness that
   should catch a defect exists, the defect is reverted on a scratch branch and
   the harness must rediscover it before its "gate" box is checked. A suite
   that cannot rediscover a known bug is a suite whose value is unmeasured.

Status: **open** → **fixed** (commit noted) → **gated** (rediscovery verified).

Until 3.3.0 no row had ever reached **gated**, although several said "gated by ..."
inside their prose -- the three-state machine was described and never used.
Rediscovery is verified two ways and both count: reverting the defect on a scratch
branch and watching a tier rediscover it, or, for a defect inside one
implementation, injecting it back as a mutation and watching the named test fail.
Those are the same idea at two scales. A row is promoted only when its own prose
records that this was actually done.

| D11 | `protocol.md` §2/§4 said an application payload larger than a transport frame is **chunked by the origin** (`chunk: {i, n}`) and pointed at §6 for how — and §6 never mentioned chunking at all. | D14 | The reassembler sized its segment buffer on the peer's `chunk.n` **before** validating it, so one frame could make a destination allocate on a number an unauthenticated-at-that-layer peer chose. | D19 | A reaper run whose SSH control channel drops mid-chain is reported as a SUCCESS. Observed on the root interop tenant: the channel died partway through tier 9, reaper printed "results are not coming back" and could not rsync `out/`, and `reaper test` still exited **0** -- while `tier10.sh` was demonstrably still executing on the guest (`pgrep` confirmed it, and the guest-side log was still growing). The guest was fine throughout: no OOM, no reboot, 6 GiB free, iptables clean, 26 minutes of uptime. | the pre-push battery harness, not the repository | test infrastructure (environment) | **fixed upstream in reaper 0.1.1**, having been recorded here as "mitigated, not fixed" while the driver ran 0.1.0. | D20 | A transport-level fault left the link **up and permanently undeliverable** in four of the seven ports. Go, Rust, JS and Python dropped the offending frame and continued (`continue` / early `return`), while Java, PHP and Elixir closed -- and each side's comment claimed to be the one matching the others. Because the expected `seq` advances only on a frame that opens, a receiver that continues is left expecting a `seq` the peer has already moved past, so **every** subsequent frame fails the same check: the session is dead while both ends still believe it is up. `BONEMESH_IDLE_MS` defaults to 0, so no timer reaps it, and the break is one-directional -- the faulting side's own probes keep arriving at the peer, so the peer keeps routing through a path that can never deliver. `protocol.md` §4 already said the session is torn down. | `go/node/node.go`, `rust/src/node.rs`, `js/src/node.js`, `python/bonemesh/node.py`, and for the silently-skipped framing fault `php/src/Node.php` | wire-visible divergence | fixed (3.3.1): all seven now tear the session down and announce it as `bye{reason:"protocol-error"}` before closing, so the node re-dials into a fresh session instead of holding a corpse. Two ports were worse than divergent: JS raised a framing-violation item while its push callback was set, which fell through to an empty waiter list and was queued where nothing ever drained it, and PHP's established-phase branch was a literal `continue` -- so in both a frame that is not one JSON object was silently skipped. Each port has a seq-gap test asserting the teardown *and* reading the reason off the wire, plus a guard test that an unrecognized inner `type` does neither (§8 requires tolerating it); every assertion mutation-checked. One narrower property is gated in two ports only: the bye must be sealed on the *faulting* link rather than on whichever link is current for that peer, since a reconnect can land in between and a lookup by label would then write an unopenable frame onto a healthy session. All four ports that looked the peer up were changed to write the faulting link directly, but only Go and Python have the staged two-link test for it (it needs a second link for one peer constructed without going through the register path, which would close the displaced link and destroy the state under test); Rust and JS carry the same corrected shape unguarded. |
| D21 | Three ports never enforced §0's frame cap on the wire path at all, two of them with **no bound whatsoever**, so a peer that never sends a newline could grow their buffers without limit -- D7's class, reintroduced per-port. Rust's `read_line` was a bare `read_until(b'\n')`, and `frame::classify` together with both `HANDSHAKE_CAP` and `TRANSPORT_CAP` were dead code in that port, called only by the corpus checker. PHP enforced its caps per *line*, which only happens once a newline arrives, while `conns[$id]['buf']` accumulated unbounded before that. Elixir was bounded but by the wrong number and for the wrong reason: `Frame.transport_cap/0` was called only by its corpus checker, and what actually limited a line was the socket's `{:packet, :line}` `packet_size` of 200000 -- so it accepted frames three times over §0's 65536 that every other port refuses. | `rust/src/node.rs`, `php/src/Node.php`, `elixir/lib/bonemesh/node.ex` | unbounded input | fixed (3.3.1): all three enforce §0's caps while reading, and an oversize frame is a `protocol-error` close rather than a silent one. Rust's reader now distinguishes an oversize frame from a closed stream, because only the former is the peer's fault. PHP's guard uses `>=`, matching Go's `readLine` and Java's `FrameCodec`: a buffer that has reached the cap with no newline in it cannot go on to yield a line within the cap. Rust and PHP have a test that floods without a newline and asserts the named close, and Elixir's sends a properly sealed frame that is merely too large -- the only thing wrong with it is its size, so a cap check that fired only on garbage would not satisfy it; the Rust one is also the reason that port's test helper takes a read deadline, since a regression there would otherwise hang the suite instead of failing it. |
| D22 | `protocol.md` §8 defined a `rekey-failed` close reason that **contradicted `security.md` §6**, which specifies that a rekey the peer ignores degrades safely and keeps the old keys so that a peer predating the feature keeps working. No port emitted it, and implementing it as written would have broken the guarantee #17 chose deliberately over capability negotiation; §6 also states that forward secrecy depends on neither rekey nor idle teardown, so nothing was at stake in closing. The registry nearly gained this as "spec'd, implemented by nobody" -- the same shape as broadcast -- when the correct resolution was the opposite direction. | `spec/protocol.md` §8 | spec contradiction | fixed (3.3.1): the reason is removed, with §8 now stating why no such reason exists and §6 cross-referencing it from the degrade that makes it unnecessary (ADR #28). §6 also now records that the attempt is retried on a later heartbeat while the trigger holds, which is what the code does and what makes the degrade recoverable rather than permanent. The sibling `protocol-error` went the other way and is now emitted by all seven (D20). |
| D23 | In the JS port, `socket.destroy()` immediately after `socket.write()` **discards whatever is still buffered**. Measured on this host: 200 KB written and then destroyed delivers about 49 KB. The `bye` frames written on that pattern are ~100 bytes and so fit the socket buffer in practice, which is why nothing has ever observed it — but the margin is the buffer's, not the code's, and a bye queued behind an in-flight `data` frame is not guaranteed that margin. | `js/src/node.js` — `kill()`'s `shutdown` bye, and the graceful-bye teardown | implementation (latent) | fixed (3.3.1). A `closeAfterFlush` helper solves both halves at once: `end()` starts the flush and a 5000 ms deadline destroys the socket if the peer never drains it, so a bye is delivered without a wedged peer turning into a descriptor leak. Used where the close is deliberate and something queued is meant to arrive -- `kill()`'s shutdown bye, the idle bye, the graceful-bye teardown, the new protocol-error path. Probe-timeout death, a rejected handshake and a dial that lost the tiebreak still destroy outright, for a stated reason: there is nothing to deliver and waiting out a deadline for a peer already proven gone buys nothing. The fix was wrong on the first attempt and the test is what said so -- with the flush started, an inbound probe still drew an `echo` reply, and writing to an ended stream raises ERR_STREAM_WRITE_AFTER_END, which destroys it and discards the very buffer the flush existed to deliver; `sendToLink` now refuses a socket that is closing. Two tests, both mutation-checked against all three properties. The oracle is the data rather than the bye, because a ~100-byte bye survives `destroy()` and would have passed on the old behaviour: a peer that stops reading lets ~1 MB queue, and before the fix 2 of 60 messages arrived. The deadline test twice passed vacuously before it earned its place -- first because 1 MB simply drained into the receiver's kernel buffer, then because a 20 s window let the peer's own 15 s probe-timeout sweep close the socket instead -- so it now stages the blocked flush explicitly, fails if it cannot, and asserts inside a window that excludes the sweep. |
